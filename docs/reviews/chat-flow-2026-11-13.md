## Bound opening and privacy

`conversations.opening` stores identities/proofs, locale, closed public prompt
keys or a dated activity selector. It stores no copied source bodies, OCR,
quotes or arbitrary client assistant/system text. Source, image and Why selectors
must resolve to current owned records. Direct creates and binding reopens enforce
the same semantic constraints; a public hash is not treated as a signed prepare
capability. Why keeps the selected order of up to three currently supported
inspirations, including current owned photo metadata.

The API resolves display words and media and then re-proves the source and edge
identities. A controlled READ COMMITTED interleaving confirms that a changed
body cannot be served under its previous proof. Model preparation uses a shared
context-only path, avoiding UI body/media reads. Its sources obey the existing
8,000/4,000/4,000 per-kind, 1,600 per-source and 16,000 total character budgets.
Opening-absent conversations retain the existing selection, including legacy
memory isolation. Deliberate no-memory corrections omit memory-backed openings
before the ModelProvider boundary; an unrelated source edit does not stale that
reply. Existing source/revision publication fences reject an answer generated
while its bound source changes.

Application-authored context is separate from generated messages/provenance.
The first human content and position remain unchanged. Creation and replay compare
the immutable descriptor with the existing first-message identity. Old clients
and opening-absent journals remain compatible. A committed pending send keeps its
original IDs and binding after a lost acknowledgement, including source deletion.
Distinct companion lines have distinct digest-keyed journals. Source journals
survive source edits so an unsent draft remains recoverable. A definite
`conversation_opening_unavailable` refusal permits an explicit **Continue without
the opening**; it does not silently substitute new words. Transient read failures
remain retryable. Conversation deletion clears the descriptor and preserves the
existing deleted-conversation refusal; profile/account erasure cascades it.

These are synthetic local component/database observations, not deployed input,
network or provider latency measurements. Browser automation/frame scheduling
made input-to-RAF samples unsuitable for latency claims.

| 80 scroll events before the next frame | 80 storage writes | 1 frame write, plus final-position leave flush |

| Same styled browser React update median | About 1.8 ms | About 1.1 ms; fixture profiling only |
| Actual click to pending DOM in controlled browser | Pending row below viewport until 800 ms acknowledgement | Pending row and cue visible about 2.7 ms after the actual click, before acknowledgement |
| Mobile 390×844, 5 s acknowledgement / 15 s reply | No equivalent final baseline latency claim | Pending visible about 2.9 ms; stable cue height, long-wait explanation, Stop, reduced-motion dots disabled |
| Fifty photo tiles / 500 ms fake URL transport | 50 eager reads before scroll | 6 initial reads / 3 loaded, peak 3; after a 1,200 px scroll, peak remains 3 and visible tiles finish |

An intermediate thumbnail implementation reached server peak 6 because aborting
offscreen requests freed client slots while the server still worked. That failed
receipt is retained. The correction drops queued offscreen work but lets same-owner
in-flight transports settle in their slots. Scope/logout disposal still aborts and
fences results. This is not a universal remote-work concurrency guarantee across
timeouts, account changes, tabs or distributed clients. URLs live only in scoped
memory (64 cached entries, four-minute freshness against five-minute presigns).
Failure recovery is bounded, with no idle expiry polling or persistent URL cache.

One actual disposable PG17 source+Why-three fixture measured application SELECT
counts and total local route/resolver duration:
