## Original reviewed work and evidence

### 1. Restore owner visibility and revocation for every retained credential

**Medium security impact; high confidence in the UI gap. Smallest first assignment.** An account with an existing standing agent key retains a valid credential but loses its ordinary Settings discovery/revocation path. This does not widen that credential into personal memory; it makes an existing compromise harder for the owner to find and stop. Whether any particular owner currently has such keys was not inspected.

Evidence: `packages/web/src/components/SettingsPanel.tsx:64` selects only the human profile; `:139` mounts personal connections. `packages/web/src/lib/api/profile-keys.ts:14` consequently chooses `/keeper-keys`, then filters to that profile at `:18`. Signed-in devices reads `sessions`, not `agent_keys` (`packages/api/src/routes/sessions.ts:50`). Existing agent keys still authenticate through `packages/api/src/lib/middleware.ts:110`; lookup checks the hash, unrevoked state and agent type, without an expiry check (`packages/api/src/lib/agent-key-auth.ts:82`). Human-only account-scoped key listing and revocation already exist (`packages/api/src/routes/agent-keys.ts:57`, `:129`, `:162`). Backend availability is not an owner-facing remedy.

**Bounded change:** make Settings expose one account connection inventory with credential type, label/prefix, legacy scope, activity and revoke action. Reuse existing authorized list/revoke APIs. Start with discover/revoke of existing standing keys; do not restore profile creation/selection, merge memories, reveal secrets, rebind credentials or automatically revoke them. Keep personal key setup separate from retained access.

**Acceptance:** synthetic accounts with zero/one/several retained stacks and mixed session/personal/legacy keys can discover and revoke every live credential. Revoked keys immediately fail authentication; unaffected credentials retain exactly their old scope. Another account's keys are absent and cannot be revoked; standing credentials cannot administer the inventory or export memory. Test through the visible UI and real API/auth lookup using a disposable loopback DB. No migration or cloud admin dependency is expected.

### 2. Make attachment erasure durable, including outstanding PUTs

**High privacy impact when deletion fails or races an upload; high confidence in the code gap, no observed breach.** Profile deletion commits before a best-effort object sweep (`packages/api/src/routes/profiles.ts:148`, `:153`). Shelf expiry deletes the last retained inventory first (`packages/api/src/lib/deleted-shelf.ts:33`); staged expiry does likewise (`packages/api/src/lib/conversation-attachments.ts:210`). The common sweep only logs transport failures and per-object errors in a successful S3 response (`packages/api/src/lib/attachment-sweep.ts:21`). Those objects may become untracked after a transient failure.

Presign issues a five-minute PUT without persisting an upload reservation (`packages/api/src/routes/attachments.ts:471`, `:925`). A URL issued before deletion can therefore create an object after SQL erasure, even if never finalized. Account erasure is stronger for *recorded* keys: it fails on object errors and rechecks inventory before deleting SQL (`packages/api/src/lib/account-erasure.ts:87`, `:132`, `:289`). It still cannot inventory an unrecorded future PUT. Do not replace that stronger behavior with best-effort deletion.

**Bounded change:** first add transactional cleanup intent that survives profile/copy deletion, reference-aware retries and handling of S3's individual errors. Then add issuance inventory and a late-upload reconciliation mechanism. URL expiry alone is not evidence that all upload bytes are gone. Keep both sub-gates explicit; an outbox alone does not close the PUT race.

**Acceptance:** inject transport failure, HTTP-200 per-key failure and worker restart after SQL commit; cleanup intent survives and retries remove unreferenced bytes without touching a still-referenced key. Issue PUT, delete the profile/account, then complete or abandon the upload without finalization; prove eventual object removal within an explicitly documented cleanup bound. Local work can use synthetic SQL plus a faulting object-store adapter. Production completion needs authorized bucket/event/lifecycle/IAM and retry scheduling verification, plus a real failure → owner notification → recovery receipt. These remain the open gates in `docs/goals/beta-readiness.md:100` and `:76`; no destination or cloud policy was verified here.

### 3. Reduce distinct-citation query amplification on chat reads

**High potential latency/work reduction for citation-heavy threads; high confidence in call amplification, production latency unmeasured.** The initial message window is already bounded; the old full-thread initial-load finding is not the remaining problem. Current citation validation deduplicates identities, but reads them in sequential groups of three (`packages/api/src/lib/conversation-context.ts:129`). Every chunk invokes the general context reader, including principle and reading queries even when their ID lists are empty (`:37`, `packages/api/src/lib/conversation-readings.ts:14`). Material adds a third query for inspiration IDs (`packages/api/src/lib/conversation-material.ts:38`). Retained `both` conversations repeat validation against their two isolated owners (`packages/api/src/lib/conversation-context.ts:109`).

Fresh narrow probe: call the current `currentConversationReferenceGroups` with 30 synthetic three-reference message groups and a fake `select` builder returning no rows. Three repeated inspiration identities execute **3 awaited selects**; 90 distinct identities execute **90**, with all 30 output groups retained and unavailable references null. This is a current reader-call count, **not real SQL execution, HTTP timing or a successful-citation benchmark**. It confirms a concrete remaining work multiplier without reading any owner data.

**Bounded change:** use a dedicated bounded citation reader, grouped by owner/kind, skipping empty kinds. Separate source assembly from excerpt budgets so larger batches do not silently truncate valid proofs. Preserve hashes, revisions, locked wording, current support, deleted/foreign-source refusal and legacy owner labels. Do not introduce a cross-request proof cache.

**Acceptance:** first record current successful/missing/mixed citation baselines using `tools/performance/long-conversation.ts` extended only with a distinct-identity case. At pool one, target at least 50% fewer citation statements for 90 distinct identities, identical proof/output membership and no regression in repeated-reference or 30-message/load-more behavior. Use a disposable loopback DB, no providers, and distinguish real local timing from the optional 50 ms/statement transport simulation. The historical Review Next **20 statements** and chat poll **four** in `tools/performance/README.md:26` are separate leads, not fresh findings; remeasure them before authorizing another optimization of those paths. Existing instruments and `docs/goals/responsiveness-reliability.md:14` supply that gate.

### 4. Close the deployment source-trust gate before tuning login throttles

**Medium conditional security/availability risk; code behavior verified, current production topology unverified.** With `WAKA_TRUSTED_PROXY_HOPS` unset, source bucketing deliberately declines to guess. Positive values trust a right-counted forwarded entry (`packages/api/src/lib/login-throttle.ts:282`, `:298`). Identifier/device protections still exist; this is not an unthrottled-login claim. Blindly enabling a hop count could instead trust a forged header on a directly reachable origin or bucket unrelated users together.

The repository policy probe intentionally cannot attest exclusive ingress or forwarded-header trust from a public/CloudFront grant alone (`scripts/dev-source-policy.mjs:7`). Its recorded receipt has both checks false (`docs/craft/evidence/2026-10-06-beta-readiness-m4-source-policy.json:26`). Current API routing exists at `sst.config.ts:351`; repository configuration is not proof of deployed policy.

**Bounded change/gate:** obtain a fresh authorized read-only receipt of Function URL authentication/resource-policy conditions, direct-origin reachability and actual header append/overwrite behavior. Only then constrain ingress and configure a source extractor consistent with that topology. Verify forged/short/multiple forwarded chains cannot choose their bucket or bypass protections, legitimate clients behind the supported proxy do not collapse to one bucket, and identifier/device recovery remains intact. This needs cloud admin access/ingress decisions; local unit probes alone cannot close it. Run this attestation in parallel with packages 1–2, not as a guessed environment repair.
