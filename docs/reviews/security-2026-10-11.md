# CONFIRMED findings

## 1. MEDIUM — the repository walk follows symlinks and reads outside the repository

**File:** `packages/web/test/unnamed-reference.test.ts:72-82`

```ts
try { stat = statSync(path); } catch { continue; }
if (stat.isDirectory()) everyFile(path, found);
```

`statSync` resolves symlinks; `lstatSync` does not. So any symlink inside the
repository that points at a directory is walked as if it were a directory, and
`readFileSync(path, "utf8")` in the second test reads whatever is behind it.

**The concrete failure.** A symlink committed anywhere in the tree —
`ln -s /Users/yunjichung docs/x`, or a dependency's postinstall dropping one,
or a `pnpm` layout change outside `node_modules` — turns this gate into a
reader of the developer's home directory. It then reports *matching paths* in
its failure message, so a match found outside the repository is printed into
CI output. A self-referential symlink (`ln -s . sub/loop`) also multiplies the
walk.

**Tested.** I reproduced the walk verbatim on a scratch tree:

- `repo/escape -> ../outside` → the walk emitted `repo/escape/secret.txt`,
  a file outside the tree it was given. **Escape confirmed.**
- `repo/sub/loop -> .` → the walk re-entered 32 times and then stopped, because
  macOS returns `ELOOP` at the symlink-resolution limit and `ELOOP` lands in
  the `catch { continue; }`. So the amplification is bounded at roughly 32×,
  not a hang. **Resource problem is real but mild.**

There are no symlinks in the tracked tree today (only inside `node_modules`,
which is skipped), so this is latent rather than live. The suite runs in ~2s.

**Smallest correct fix** — one import and one call:

```ts
import { lstatSync } from "node:fs";
// ...
try { stat = lstatSync(path); } catch { continue; }
if (stat.isSymbolicLink()) continue;
if (stat.isDirectory()) everyFile(path, found);
```

A better fix, which also closes finding 12, is to enumerate from
`git ls-files -z` instead of walking the filesystem: the rule is about what
this repository *publishes*, and untracked local files are not that.

## 2. MEDIUM — migration 0069 can never apply on a database that recorded the pre-fix 0070

**Files:** `drizzle/migrations/meta/_journal.json` (idx 69, 70);
`drizzle/migrations/0069_inspiration_category.sql`

The journal fix is correct in itself: 0069's entry is stamped with the file's
own mtime (`1791512364893`), which sits between 0068's `1791369798790` and
0070's `1791745200000`, and `idx` has no gaps. The new structural gate in
`fresh-migrate.db.test.ts` is the right gate and I confirmed it catches what it
claims — it compares folder to journal in both directions and asserts `idx` is
dense and `when` rises.

**What the fix does not reach.** Drizzle applies by timestamp, not by index.
From `drizzle-orm@0.45.2/pg-core/dialect.js:62`:

```js
if (!lastDbMigration || Number(lastDbMigration.created_at) < migration.folderMillis) {
```

`lastDbMigration` is the newest row in `drizzle.__drizzle_migrations`. So on any
database whose newest recorded stamp is **≥ 1791512364893**, migration 0069 is
skipped — permanently, with no error. The pre-fix 0070 carried the same
`when` it carries now (`1791745200000`; the renumbering changed `idx`, not
`when`), so **any environment that ran `drizzle-kit migrate` between
`a063bd1b` and `6be2f854` will never get `inspirations.category`** — which is
the exact condition the fix was written to eliminate.

**Tested.** I queried the local database read-only:

```
drizzle.__drizzle_migrations newest created_at = 1791369798790   (= 0068)
inspirations.category                           present
conversations.initial_inspiration_id            present
```

So the local ledger stops at 0068 and both 0069 and 0070 will apply on the next
run. Both are idempotent against the hand-added columns — I verified the claim
by reading the SQL (`ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`,
and 0070's `DO $$ ... EXCEPTION WHEN duplicate_object THEN NULL`) and then by
running `fresh-migrate.db.test.ts`, which applies the whole corpus through
drizzle's real migrator on an empty database and now asserts both columns
arrive. **It passes.** No migration in this range can be applied twice
destructively.

The founder's local box is therefore fine. The deployed stages are the unknown.

**Smallest correct fix.** Do not re-stamp 0069 — moving its `when` above 0070's
breaks the ordering invariant the new gate exists to protect. Add
`0071_inspiration_category_backfill.sql` repeating 0069's two statements
verbatim (they are already `IF NOT EXISTS`, so it is a no-op wherever 0069
landed) and journal it at idx 71. That converges every environment regardless
of what its ledger recorded. Before that, the one-line check per stage is:

```sql
SELECT max(created_at) FROM drizzle.__drizzle_migrations;
SELECT 1 FROM information_schema.columns
 WHERE table_name='inspirations' AND column_name='category';
```

## 3. MEDIUM — the dictation cloud disclosure can be suppressed entirely

**Files:** `packages/web/src/pages/Home.tsx:11580-11595`;
`packages/web/src/lib/use-dictation.ts:139`

The product's one disclosure that browser speech recognition ships audio to a
third party is a single slot in a first-non-empty OR chain:

```ts
const composerState = mouthNote || composerDraft.error || recording.error
  || (dictation.error === 'dictation-denied' ? say('worldComposerDictateDenied') : '')
  || (dictation.error === 'dictation-failed' ? say('worldComposerDictateFailed') : '')
  || (dictation.firstTime && dictation.listening ? say('worldComposerDictateCloud') : '')
```

Three earlier terms win over it. `mouthNote` is set by a dozen things — a
rejected file, `'Keep one recording in each inspiration.'`, a save failure —
and `dictation.start()` does not clear it. Only the hook's `onText` callback
clears it, and that fires on the first recognition result.

**The concrete failure.** Drop a file the sniffer rejects (so `mouthNote` is
non-empty), then press the microphone. The microphone opens, audio begins
streaming to the browser vendor's service, and the bar is still showing the
file error. If the person says nothing — which is the common case for an
accidental press — the engine fires `no-speech`, which the hook deliberately
does not report, `onend` clears `listening`, and **the disclosure never
appeared at all**. On any repeat visit the microphone permission is already
granted, so there is no browser prompt either: audio leaves the device with
nothing on screen saying so.

A second, milder version: the notice is shown *after* `live.start()`, by
design ("it is a fact rather than a decision"). I think that trade is
defensible — the mic permission prompt is the consent gate and the exposure is
a different recipient rather than a new kind of data — but it means the one
suppressible notice is also the only notice.

**Also noted, not a finding:** nothing else leaks through this path. Only
`live.lang = locale` is handed to the engine; the note's existing text is never
sent, and `base.current`/`settled.current` stay in the page. `firstTime` never
resets to `false`, so the notice actually shows on *every* dictation session
within a mount rather than once — more disclosure than documented, which is
the safe direction.

**Coverage gap behind it.** `test/dictation.test.ts:209` asserts the hook's
`firstTime` flag. Nothing asserts that `worldComposerDictateCloud` ever reaches
the bar. The string appears in exactly one `src` expression and zero tests.

**Smallest correct fix** — take the disclosure out of the competition. It is
not a transient status, it is a standing fact about what is happening right
now:

```ts
const cloudNotice = dictation.listening ? say('worldComposerDictateCloud') : '';
```

and render it in the bar alongside `composerState` rather than inside it. If it
must stay in one slot, hoist it above `mouthNote` — a privacy disclosure
outranks a file error.

## 4. MEDIUM — the merge that protects the public-page settings is untested

**Files:** `packages/api/src/routes/auth-me.ts:211-232`;
`packages/api/src/routes/auth-profile.test.ts:260`

This is the one the brief called the highest-value thing to get right, and the
behaviour **is** right. `PATCH /auth/me/profile` is a replace for `name` and
`preferredLocale` (both required by `profileSchema`) and a **merge** for the
three public fields:

```ts
const normalizedHandle = parsed.data.publicHandle === undefined
  ? current.profile.publicHandle : ...;
const publicProfileEnabled   = parsed.data.publicProfileEnabled   ?? current.profile.publicProfileEnabled;
const publicTopOfMindEnabled = parsed.data.publicTopOfMindEnabled ?? current.profile.publicTopOfMindEnabled;
```

So the rename path in `SettingsPanel`, which sends only
`{ name, preferredLocale }`, **cannot** clear a handle or flip a toggle. I
traced every caller: `Home.tsx:2911` (rename), `Home.tsx:2936` (the public
save, which sends all three explicitly), and `Onboarding.tsx:90`. There is no
fourth.

**What is wrong is that nothing holds the `??` in place.** Those three lines are
the entire reason the settings move is safe, and no test asserts them. Every
test in `auth-profile.test.ts` that touches the public fields supplies them.
The one rename-only test — `"persists display names containing spaces"` at
line 260 — asserts with `toMatchObject({ name: "Mina Park" })`, which by
definition passes while `publicHandle: null` and `publicProfileEnabled: false`
sit beside it in the same `set()` call. A future editor "simplifying"
`profileHandler` to plain assignment would turn every rename into a silent
public-page shutdown and the suite would stay green.

**Smallest correct fix** — one test, four lines:

```ts
it("leaves the public page alone when a rename does not mention it", async () => {
  const db = fakeDb({ profile: { ...profileRow, publicHandle: "mina", publicProfileEnabled: true } });
  await request({ name: "Mina Park", preferredLocale: "en-US" });
  expect(db.setCalls[0]!.values).toMatchObject({
    publicHandle: "mina", publicProfileEnabled: true,
  });
});
```

`toMatchObject` is correct here because the assertion now *names* the fields
that must survive.

## 5. LOW — an armed delete confirmation survives collapsing its disclosure

**File:** `packages/web/src/components/SettingsPanel.tsx:137-139, 272-281`
(and the agent-erase variant at 199-212)

`confirmDelete` lives on `SettingsPanel`, not inside the `Group`. Collapsing
the danger disclosure unmounts the button but leaves the flag set, so:

1. open the gear, expand `profileDelete`, press once → armed
2. collapse it, expand `profileMemoriesTitle`, read it, come back
3. one press erases the account

The panel unmounts on close, so the window is one open session. The button's
label does read `worldDeleteItAnyway` throughout, which is the thing that keeps

and the same shape for the agent arming (`if (open !== "agents") setBusyAgent(null)`),

## 6. LOW — the link tile builds an `href` from input with no protocol guard

**File:** `packages/web/src/components/InspirationComposer.tsx:164`

```tsx
) : item.type === 'link' && item.url ? (
  <a className="jar-tile-face jar-tile-link" href={item.url} target="_blank" rel="noreferrer">
```

Not reachable today, and I chased it to the end:

- `inspirationLinks()` only matches `/https?:\/\/[^\s<>"']+/gi` and round-trips
  through `new URL`, so text-derived link media is always `http:`/`https:`.
- `inspirationWithPendingLink()` rejects anything else explicitly
  (`if(!['http:','https:'].includes(url.protocol)...) throw new Error('invalid_link')`),
  and the server's `createInspirationSchema` rejects it again.
- `inspiration-draft-store.ts` types `'link'` in its media union but nothing
  writes one, so a restored draft cannot carry an arbitrary protocol.

So this is defence-in-depth, not a hole. It is worth closing because the
sibling component already has the guard and this one does not —
`AttachmentPreview.tsx:5` is the exact helper:

```ts
try { const url = new URL(value ?? ''); return ['http:','https:'].includes(url.protocol) && !url.username && !url.password ? url.toString() : null; } catch { return null; }
```

**Smallest correct fix:** export that helper and run `item.url` through it,
falling back to the `jar-tile-name` span when it returns null.

## 8. LOW — a stale positional caller silently disabled the retrieval-quality gate

**File:** `tools/e2e/conversation-retrieval-quality.ts:96`

`readConversationContext` gained `initialInspirationId` as a new **positional**
parameter between `initialPrincipleId` and `queryVector`. Every caller in
`packages/api` was updated, including `conversation-retrieval.db.test.ts:38`,
which correctly gained a sixth `undefined`. One caller was not:

```ts
const hybrid = await readConversationContext(fixture.db as never, owner, query,
  undefined, undefined, vector, value => { trace = value; });
```

`vector` (a `number[]`) now lands in the `initialInspirationId` slot and the
trace callback lands in `queryVector`. The hybrid arm of the retrieval-quality
harness therefore no longer measures hybrid retrieval, and it does not fail
loudly — it just reports lexical numbers under a `hybrid` key.

Nothing catches it: `packages/api/tsconfig.json` is `"include": ["src/**/*.ts"]`
and no package typechecks `tools/`, so the type mismatch never reaches `tsc`.
I checked the other four `tools/` callers (`tools/performance/long-conversation.ts`,
`tools/performance/run.ts`) — all pass three or four arguments and are
unaffected.

Not a production path. It is in here because a quality gate that silently stops
measuring is how a retrieval regression ships.

**Smallest correct fix:** insert the missing `undefined` —
`(..., query, undefined, undefined, undefined, vector, value => {...})`. The
durable fix is an options object for the last four parameters; six positional
optionals is how this happened.

# What I checked and found correct

These are deliberate negative results. They are the load-bearing half of this
review.

### The central question: cross-profile inspiration access — CLEAN, three ways

One profile cannot pin, read, or cause a reply to read another profile's
inspiration. Each layer was checked independently:

1. **Structurally impossible to store.**
   `drizzle/migrations/0070_conversation_inspiration_start.sql` adds the FK on
   the *pair*, against the unique pair it targets:
   `FOREIGN KEY (profile_id, initial_inspiration_id) REFERENCES public.inspirations(profile_id, id)`.
   A single-column FK would have made tenancy a habit; this makes it an
   invariant. I confirmed the constraint is live and refuses, not merely
   declared — `conversations.db.test.ts` asserts
   `UPDATE conversations SET initial_inspiration_id=<foreign>` rejects with
   SQLSTATE `23503`, and **that test passes against the local test database.**
   The column-list `ON DELETE SET NULL (initial_inspiration_id)` is also
   correct and load-bearing: a bare composite `SET NULL` would null
   `profile_id` and detach the conversation from its owner.

2. **Refused at both writers, before the FK.** `requireOwnedInspiration`
   (`conversations.ts`) filters on `eq(inspirations.profileId, profileId)` and
   is called on the `POST /` create path and the `PATCH /:id` path. Both return
   404 — the same answer a deleted keep gives, so the parameter cannot be used
   to probe which profiles hold which inspirations. Tested: `POST` and `PATCH`
   with a foreign id both 404, the stored pin is left untouched rather than
   half-applied, and the foreign sentinel string appears nowhere in the response.

3. **Owner-scoped again on the read.** The pin in
   `conversation-context.ts:76` goes through
   `readConversationMaterial(db, profileId, [], ids)`, whose `ids` branch is
   `.where(and(eq(inspirations.profileId, profileId), inArray(inspirations.id, ids)))`.
   A foreign id yields no row and the pin simply does not appear. Tested
   directly in `conversation-context.db.test.ts`: a foreign pin returns only
   the legitimately retrieved row and the serialised context does not contain
   the foreign sentinel.

Also correct and worth recording: `profileId` reaches these handlers only from
`resolveTargetProfile`, which defaults to the session's own profile, requires
same-account for any named profile, answers 404 (not 403) for a profile in
another account, and runs the operation matrix — with `'write'` for every
non-GET method, so PATCH is a write. The whole router sits behind
`requireAuth` **and** `humanSessionsOnly`, so an agent credential cannot reach
conversations at all. The pin is also correctly **not** applied on the
historical-citation path (`referenceIds` present), which would otherwise have
spent the shared character allowance of the record being re-opened and reported
an unchanged citation as changed.

I ran `conversations.db.test.ts`, `conversation-context.db.test.ts`,
`conversation-replies.db.test.ts` and `fresh-migrate.db.test.ts` against the
local test database: **23 + 3 tests, all passing.**

None of the five server route families changed in this diff; I read each

| `/api/agent-keys` | `requireAuth` + `humanSessionsOnly` |

The deleted files are web-side wrappers only (`lib/api/keeper-keys.ts`,

On "an attacker can still call it": calling any of these needs a valid session.
The session cookie is `HttpOnly; SameSite=Lax`, which blocks the cookie on
cross-site POST/PATCH/DELETE, and `lib/mobile-cors.ts` allowlists exactly
`capacitor://localhost` and `https://localhost`, rejects any cross-origin
request that carries a `Cookie` header outright, and allowlists methods and
headers on preflight. There is no origin reflection. So the orphaned write
endpoints are not reachable from a hostile page.

### Dictation — no leak beyond the audio itself

reported as errors; a blocked microphone is separated from a broken one. The

### Markup and injection — CLEAN

- No `dangerouslySetInnerHTML`, `innerHTML`, `outerHTML`,
  `insertAdjacentHTML`, `eval`, or `new Function` anywhere in
  `packages/web/src` or `packages/api/src`.
- `ConversationText.tsx` renders model and user text as React text nodes only:
  it produces `<p>`, `<ul>/<ol>`, `<strong>`, `<code>` and never an anchor or

  `<img src=x onerror=alert(1)> [link](javascript:alert(1))` and asserts

### File validation and the drop target — CLEAN

The `<input accept>` list is images only, but `accept` is advisory and the drop
and paste handlers take anything, so the real gate is
`inspectInspirationPhoto` (`lib/inspiration-photo.ts`) — and it is the right
kind: it reads the first 64 bytes and matches magic numbers for JPEG, PNG, GIF,
WebP, and the `ftyp` brands for AVIF/HEIC/HEIF, ignores both the filename and
the browser's MIME guess, enforces 25 MB, rejects empty files, and **does not
accept SVG**. A file that fails is kept in the shelf carrying its
`validationError` rather than silently dropped, and `keep-ready.ts` blocks Save
while any invalid file is present, so a refused file cannot be uploaded. Audio
is bounded the same way (25 MB, `type.startsWith('audio/')`, one recording per
inspiration). The drop handler respects the same `blocked` guard the page uses
everywhere else.

### `GoogleSignIn.tsx` — presentation only, and it is not even in the diff

`git diff --stat ffee792a~1..HEAD -- packages/web/src/components/GoogleSignIn.tsx`
is **empty**. The file is byte-identical. Only the CSS surface changed, from a
solid white pill to Google's published neutral-dark button surface; the
four-colour G mark is drawn with its own hexes inside the unchanged `.tsx`. The
OAuth flow — `window.location.assign(googleLoginUrl(returnTo))`, the

claiming white was mandatory was half right and the new one states the
distinction correctly: recolouring the *mark* is the phishing signal, and
Google publishes three button surfaces for exactly this reason.
