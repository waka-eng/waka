# The two-tabs audit — one session, two windows

**Date:** 2026-08-26
**Status:** measured by hand; findings below, no defect found.

## Why it was worth asking

The world is optimistic — a keep draws its orb before the server has agreed —
and this session added a second refetch on top of that (`absorbBoard`, after a
keep and on returning to the tab). Optimism plus background refresh is where
two windows on one account usually start disagreeing, and nothing had ever
opened two.

## What happens

```
A keeps something          A holds 1      B holds 1
B keeps something          B holds 2      A holds 1   ← A untouched
```

**A staying at 1 is correct**, and it is the founder's law rather than a
tolerance: *the world never moves unless the user moved it.* A window nobody
is looking at must not repaint itself because something happened elsewhere.

The question is what happens when they come back to it.

```
A hidden 30s, then shown   A holds 2
```

It catches up. That is the `visibilitychange` refresh added earlier today —
the one that used to refresh inspirations, agent walls and the sky, and skip
the board.

## The dead-session case, which is the one that matters

Sign out in B while A still shows the world. A does not know, and correctly
does not: nothing has moved it. Then type into A and press save:

> **That didn't keep. The words are still here — you are signed out. Sign in
> and it is still here.**

The best available behaviour. It names what happened, it does not pretend, and
**it keeps the words** — the sentence is still in the box for whoever signs
back in. A person who typed a paragraph into a tab whose session died
somewhere else loses nothing.

## What the walk got wrong first

The catch-up test reported **A after returning: 1** — the refresh apparently
not firing.

It was the harness. Headless Chromium keeps every page in a context
`visible`, so `bringToFront()` never fires `visibilitychange`; A was never
hidden and the test was measuring nothing. Caught by printing
`document.visibilityState` instead of assuming it.

Reported as written, it would have been a fabricated regression in code added
hours earlier, and the "fix" would have been changes to a handler that was
already correct.

The corrected version overrides what the page reports and dispatches the
event, which tests **the handler**. The browser's own firing of it is a
separate claim this walk does not make — worth stating, because the difference
between "the code is right" and "the browser will call it" is exactly the gap
the first version fell into.

## Still unmeasured

  renaming the same room within a second of each other. This walk had them
  take turns.
- **The real browser firing.** As above: the handler is proven, the
  integration is assumed.
